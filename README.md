# Резервная одометрия трамвая по модели

Решение команды для трека **«Резервная одометрия по модели»** хакатона от
Московского транспорта, МТТЕХ и «Транспортные инновации Москвы».

Задача: в реальном времени оценивать скорость и пройденный путь трамвая,
используя только внутренние сигналы подвижного состава (положение ручки
контроллера машиниста, скорости вращения передней и задней тележек) —
без GNSS и IMU, с компенсацией проскальзывания колёс.

## Состав решения

- `src/tram_vehicle_msgs` — пакет с сообщениями, предоставленный организаторами
  (`VelocitySensor`, `DriverControllerCommand`).
- `src/tram_reserve_odometry` — наш ROS2-пакет с узлом `reserve_odometry_node`.

## Требования

- Ubuntu 22.04 (в нашем случае — WSL2)
- ROS 2 Humble

## Сборка

```bash
cd ~/tram_ws
colcon build
source install/setup.bash
```

## Запуск

```bash
# терминал 1 — узел одометрии
source ~/tram_ws/install/setup.bash
ros2 run tram_reserve_odometry reserve_odometry_node

# терминал 2 — проверка результата
source ~/tram_ws/install/setup.bash
ros2 topic echo /result/velocity

# терминал 3 — проигрывание тестовой записи
source ~/tram_ws/install/setup.bash
ros2 bag play <путь_к_папке_прогона>
```

## Входные и выходные топики

| Топик | Тип | Направление |
|---|---|---|
| `/vehicle/front_bogie_velocity` | `tram_vehicle_msgs/msg/VelocitySensor` | вход |
| `/vehicle/rear_bogie_velocity` | `tram_vehicle_msgs/msg/VelocitySensor` | вход |
| `/vehicle/driver_position_cmd` | `tram_vehicle_msgs/msg/DriverControllerCommand` | вход |
| `/result/velocity` | `tram_vehicle_msgs/msg/VelocitySensor` | выход |
| `/result/position` | `nav_msgs/msg/Odometry` | выход |

## Алгоритм

1. **Простая модель разгона/торможения** по положению ручки контроллера:
   скорость меняется пропорционально положению ручки (коэффициенты
   `model_gain_accel` / `model_gain_brake`, параметры узла).
2. **Одометрия по тележкам**: скорости передней и задней тележки
   усредняются; при этом сравнение показаний двух тележек используется
   как индикатор проскальзывания колеса — если расхождение превышает
   порог (`slip_threshold`), доверие к сырой одометрии снижается, а вес
   модели в итоговой оценке скорости увеличивается.
3. **Итоговая скорость** — взвешенная сумма модели и одометрии тележек,
   вес переменный (растёт при подозрении на слип).
4. **Позиция** — классический dead reckoning: интегрирование итоговой
   скорости по времени между сообщениями (используется исходная
   временная метка сенсора, а не время получения сообщения — это важно
   для сверки с эталоном).

## Известные ограничения

- Коэффициенты модели (`model_gain_accel`, `model_gain_brake`) пока не
  откалиброваны методом наименьших квадратов — сейчас модель используется
  только как резервный источник на случай обнаруженного проскальзывания
  (`model_weight` намеренно установлен в 0, чтобы не искажать уже точную
  оценку по одометрии в штатном режиме).
- На проверочных записях с GNSS (`30639_*`) чистая одометрия по двум
  тележкам (без учёта модели) даёт RMSE ≈ 0.05 м/с относительно GNSS —
  подтверждено скриптом `scripts/evaluate_accuracy.py`.
- Не реализована коррекция накопленной ошибки на остановках (Zero-Velocity
  Update) и сверка по профилю скорости на характерных участках трассы —
  требует карты маршрута/путевого графа.
- Поле `covariance` в `/result/position` пока не заполняется индикатором
  надёжности оценки.

## Проверка точности

Для локальной проверки точности используется `scripts/evaluate_accuracy.py`
— он повторяет алгоритм узла в чистом Python поверх записанного бэга и
сравнивает результат с референсной GNSS-скоростью (доступна только в
части записей датасета, например `30639_*`; в самом решении GNSS не
используется — только для проверки).

Запуск:
```bash
source ~/tram_ws/install/setup.bash
python3 scripts/evaluate_accuracy.py <путь_к_папке_бэга>
```

Результаты на трёх проверочных записях (RMSE скорости относительно GNSS):

| Запись | RMSE, м/с | MAE, м/с |
|---|---|---|
| 30639_253671cc | 0.052 | 0.042 |
| 30639_9c362687 | 0.168 | 0.053 |
| 30639_c31df386 | 0.061 | 0.046 |

В процессе проверки был найден и исправлен баг: датчики скорости тележек
(`VelocitySensor.velocity`) отдают показания в км/ч, а не в м/с — это
не было указано в определении сообщения. После пересчёта в м/с и
снижения базового веса нескалиброванной модели до 0 (модель теперь
подключается только при обнаруженном проскальзывании) точность по
чистой одометрии практически совпала с GNSS.

## План развития после хакатона

- Калибровка параметров модели методом наименьших квадратов по всему
  датасету прогонов.
- Zero-Velocity Update: сброс накопленной ошибки пути на известных
  остановках по карте маршрута.
- Сверка по профилю скорости на стрелках/характерных поворотах как
  дополнительный тип «чекпоинта».
- Расширяемая архитектура детектора чекпоинтов, допускающая добавление
  других источников коррекции в будущем (например, по характерным
  электрическим меткам на линии).
- Заполнение `covariance` в `/result/position` на основе рассогласования
  модели и одометрии как индикатора надёжности оценки.

## Соответствие ожидаемой архитектуре решения

Наша модель тягового привода и продольной динамики — упрощённая нелинейная
модель: тяга/торможение пропорциональны положению ручки контроллера,
сопротивление движению — нелинейный член, пропорциональный квадрату
скорости (объединяет аэродинамическое сопротивление и сопротивление
качению в один калибруемый коэффициент).

Сознательно не реализованы отдельно (out of scope из-за ограничения по
времени, входят в план развития): масса состава и радиус колеса как
отдельные параметры, передаточные коэффициенты привода, уклон пути,
сопротивление на кривых участках, потери в приводе, явное ограничение
по сцеплению колёс с рельсом. Часть этих эффектов при калибровке методом
наименьших квадратов частично компенсируется в едином коэффициенте тяги,
но без явного физического разделения.
